# Reproducing the BMVC 2026 paper

Every figure, table and number macro that `papers/blob_boards_bmvc.tex` and
`papers/bmvc_supp.tex` read is either generated by a tracked script from
declared data, or declared `static` below with its provenance. The index is
enforced: `test/runtests.jl` (`make check` in `papers/`) runs
VisualGeometryToolkitEval's `reproduce_index_violations` over both documents and
fails on any asset the paper reads that this index does not cover, a missing
or non-writing generator, a static asset without provenance, or a number from
a generated macro file re-typed as a literal in the prose.

## Install

Julia 1.12 (juliaup). The stack is registered in CauRegistry (and submitted to
General); until it is in General, add both registries once (General first: Pkg
adds it on its own only to an empty depot), then instantiate the project:

```bash
julia -e 'using Pkg; Pkg.Registry.add("General"); Pkg.Registry.add(url = "https://github.com/prittjam/CauRegistry.jl")'   # once per depot
julia --startup-file=no --project=bmvc2026 -e 'using Pkg; Pkg.instantiate()'
```

## One command

```bash
julia --startup-file=no --project=bmvc2026 bmvc2026/scripts/regenerate_paper.jl        # results + CPU assets (the sweeps need CUDA)
julia --startup-file=no --project=bmvc2026 bmvc2026/scripts/regenerate_paper.jl --gpu  # + the GPU figures
cd bmvc2026/papers && make                                                           # supplement, then paper
```

(`make figures` / `make figures-gpu` in `papers/` run the same.) The run
starts from the INPUTS alone and regenerates every result on the way to the
paper's assets; nothing is promoted, copied into the dataset or read from a
previous run by name.

**Regenerating today vs the published paper.** A regeneration from the
inputs with the current code and configs of record (2026-10-15) reproduces
the AprilTag and ArUco results exactly (every detection bit for bit, every
number at printed precision). The BlobBoards numbers differ slightly from the
published ones: the detector changed after publication, and the half-width of
record is now 0.9646 px (5 px when the paper was made). Rerunning at 5 px
attributes the moves: the detector changes account for most (the flip counts,
the occlusion rotation medians), the half-width for a few detection rates
(±1 point). The recorded configuration differences between the published
run (2026-08-26) and the config of record: `outlier_halfwidth` 5 → 0.9646 px;
`adapt.cutoff` now from the gallery (v6); `adapt.init` and `store` fixed in
code; the local optimization stated explicitly (`student_t_uniform`) and
`undistortion = "global"`; `min_similarity`, `peak_threshold` and the NMS
cutoff unchanged. The assets under `papers/` are the published snapshot and
are not replaced.

## Inputs and results

Only inputs are published (`configs/data_artifacts.toml`): the captures, the
motion tracker's raw per-frame exports, the cameras of record, the board
definitions, the synthetic occlusion images, the descriptor networks and the
board gallery. Every result is produced by a codified stage into a keyed run
directory under `results_root()` (`CAU_RESULTS_ROOT`, default
`bmvc2026/data/exp_pro`) and found again through the stage's config of record
→ its run key → its directory (`src/runs.jl`, DrWatson-style; the evaluation
names its upstream configs in `configs/figures/evaluation.toml` `[runs]`). A
stage whose run is complete is skipped; a changed config is a new run.

| stage | generator | config of record | run directory |
|---|---|---|---|
| motion-capture records (stage 0) | `scripts/convert_formats.jl` | `configs/convert_formats.toml` | `convert_formats-<key>/` |
| BlobBoards detections (bb, calibration_bb) | `scripts/go_bmvc2026.jl` (GPU) | `configs/bmvc2026_260527.toml` | `bb-<key>/` |
| the no-disambiguation ablation (flip table) | `scripts/go_bmvc2026.jl --run-config=…` (GPU) | `configs/bmvc2026_260527_noflip.toml` | `bb-<key>/` |
| BlobBoards on every occlusion level | `scripts/go_bmvc2026_occlusion.jl` (GPU) | `configs/bmvc2026_260527.toml` | `occlusion-<key>/` |
| AprilTag + ArUco on every subset | `scripts/detect_baselines.jl` → `scripts/baselines/detect_markers.py` (pixi env `baselines`, `bmvc2026/pixi.toml`) | `configs/baselines.toml` | `baselines-<key>/` |
| hand-eye calibrations | `scripts/make_hand_eye.jl` | `configs/figures/evaluation.toml` | `hand_eye-<key>/` |
| pose-error cells | `scripts/make_pose_results.jl` | `configs/figures/evaluation.toml` | `pose_results-<key>/` |

`tests/data_tests.jl` holds the line: every run resolver points into
`results_root()`, no driver joins a `data_root()` path with a result kind, and
the inputs tier holds input kinds only.

**The AprilTag/ArUco baselines** are a faithful port of the external
evaluation code (BlobBoards-Evaluation 88bca9f, `evaluation_pipe/pose_extractor.py`
and `pose_estimators.py`; the archive ships in the inputs tier under
`provenance/`): dt-apriltags 3.1.7 (`tagStandard41h12`, decimate 2, refine
edges, sharpening 0.25), OpenCV 4.13.0.92 ArUco (`DICT_ARUCO_MIP_36h12`,
ArUco3 detection), per-tag `SOLVEPNP_IPPE_SQUARE` on the undistorted image,
numpy 2.4.2, Python 3.14.3 — every setting in `configs/baselines.toml`. It
reproduces the published exports bit for bit (poses, ids, camera matrix;
1318 images), all but the wall-clock times.

## Data tiers

`data_root()` (src/data.jl) resolves the dataset: `CAU_DATA_ROOT`, the
project's `data/exp_raw` symlink, the BlobBoards `data_dir` preference, or the
Zenodo artifact view (`Artifacts.toml`, lazily downloaded per tier). The tiers
a generator needs are named in the `data` column:

| tier | holds |
|---|---|
| `inputs` | `bb_absolute_pose_inputs`: the raw motion-capture exports, the cameras of record, the board definitions, the teaser photos, and the provenance material (`provenance/`: the BlobBoards-Evaluation code archive, the upstream calibration exports) |
| `images` | `bb_absolute_pose_images_260527`: the evaluation, calibration and intrinsic-calibration captures |
| `occlusion-LL` | `bb_absolute_pose_occlusion_LL_260527`: the synthetic occlusion images at level LL (inputs with provenance: BlobBoards-Evaluation 88bca9f `evaluation_pipe/occlusion_generator.py`, hand-clicked corners and a MAGSAC homography per board) |
| `assets` | `bb_assets`: the descriptor networks of record and the evaluation board gallery |

**Cameras of record** (inputs): each session's camera is
`<session>/calibration/<camera>.json` (vgio/cameras/v3 with its calibration
block), found by `camera_of_record` (src/data.jl). It is the exact native port,
by `scripts/import_cameras.jl` (config of record `configs/import_cameras.toml`,
run once; `test/cameras_tests.jl`: K and lens bit for bit), of the upstream
`calibrate_pinhole` export (OpenCV `calibrateCamera`, 6×7 chessboard of 0.05 m
squares, `CALIB_RATIONAL_MODEL` with k3–k6 fixed; its error statistic is a
mean, stated in the block's note), which ships in the inputs tier under
`provenance/calibration/`. The images tier is record 1.0.0's tarball reused
unchanged; its camera files are superseded and never read.

## Operating points (tuning)

Tuned values are selected on the validation side of a registered scene split
(VisualGeometryToolkitEval `configs/splits.toml`; `blobboards_cross_session`: tune on
260521/bb, report on 260527/bb — 260527 is never read by a tuning step) by
VisualGeometryToolkitEval's coarse-fine search and stored in its tuning artifacts
(`save_coarse_fine_artifact`) in the keyed, add-only run directory
`results_root()/tuning/<step>-<run_key>`, beside its `_config.toml` and
`_provenance.toml`. A consumer reads them through VisualGeometryToolkitEval
`deployed_setting` (paths in src/operating_points.jl), which refuses a search
that hit its window's edge on any axis, and `test/operating_points_tests.jl`
holds the configs of record to the artifact each value was adopted from

## Paper asset index

Paths are relative to `bmvc2026/`. `kind` is `generated` (the generator
writes it; regenerate, never edit) or `static` (made by hand; `provenance`
says by whom, how and from what). `config` is the generator's config of record
under `configs/figures/`: every parameter it uses (frame picks, crops, seeds,
panel lists, sizes, inputs, output names) lives there, not in the script, and
the script declares it (`# reproduce: reads`). The evaluation drivers
(`error_distributions.jl`, `flip_table.jl`, …) are run by `regenerate_paper.jl`
and read their config of record `evaluation.toml`. Every run
writes a record — effective `_config.toml`, `_provenance.toml` (DrWatson
`tag!` git commit, config source, run key, inputs) and `_outputs.toml` — to
the keyed directory `plots/records/<generator>-<run_key>/`
(`src/paper_assets.jl`).

## Reviewing a regeneration

Generators write under `papers/images` and `papers/figures` unless
`BB_PAPER_IMAGES` / `BB_PAPER_FIGURES` point elsewhere
(`src/paper_assets.jl`). To change a submitted asset, regenerate into a
scratch tree, compare against the tracked file (rasterise PDFs at a fixed
DPI; SSIM/PSNR and a difference image for rasters, exact equality for tables
and macros, detection-level deltas for overlays), and replace the tracked
asset only once the comparison is signed off.
